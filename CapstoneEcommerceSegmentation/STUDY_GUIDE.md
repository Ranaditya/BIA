# Developer Study Guide: E-commerce Customer Segmentation

This guide explains how the capstone converts transaction-level records into customer groups, how to read the evaluation output, and what conclusions the current design can and cannot support. The workflow is implemented across the Python modules in this folder and orchestrated by `main.py`.

## 1. Frame the Analytics Problem

Each source row represents a transaction line: one stock item on an invoice. The business question is not simply “which products sold?” but “which customers behave similarly, and how might the business engage them?”

This project has two related but distinct tasks:

- **Customer segmentation (unsupervised):** group customers from historical behavior without a pre-existing segment label.
- **Segment-label classification (supervised):** learn to reproduce labels generated by the clustering step.

The second task is not yet a future-purchase predictor. To predict future behavior, the project would need a future outcome, such as whether a customer purchases in a later 90-day window, and a time-based validation design. See [Section 11](#11-interpretation-and-methodological-limits).

## 2. Understand and Load the Data

The input is `data/data.csv`, a transaction table with `InvoiceNo`, `StockCode`, `Description`, `Quantity`, `InvoiceDate`, `UnitPrice`, `CustomerID`, and `Country`.

`load_raw` in [data_loader.py](data_loader.py) uses pandas to:

- parse `InvoiceDate` as datetime
- read `CustomerID` as a nullable string, so missing values do not force an integer dtype
- read the file as Latin-1, which supports the currency characters in this CSV
- resolve relative paths from the project directory, regardless of the shell's current directory

`describe_raw` reports row/column shape, date range, unique customers and invoices, null counts, and the number of countries. This is the first data-quality checkpoint: understand missingness and coverage before deleting anything.

The saved run reports 541,909 raw rows and 4,372 distinct non-null CustomerIDs before cleaning. The dataset source citation and license are not recorded in this repository; preserve that provenance in a submitted report.

## 3. Clean Transaction Lines

`clean_transactions` in [preprocessing.py](preprocessing.py) works on a copy, applies the filters in sequence, reports the number removed at each stage, and creates `TotalPrice`.

| Step | Rule | Why it is applied |
| --- | --- | --- |
| Missing customer | Drop rows without `CustomerID` when the option is enabled. | Customer-level aggregation requires a customer key. |
| Cancellation | Drop invoice numbers beginning with `C` when enabled. | Cancellation lines should not count as completed purchases in this analysis. |
| Price | Keep `UnitPrice >= 0.01`. | Remove zero and negative prices and enforce the configured minimum. |
| Non-numeric stock code | Keep rows whose `StockCode` is numeric. | Exclude service or adjustment codes (such as POST and BANK CHARGES). Trade-off: this also drops product variants with letter suffixes, such as `85123A`. |
| Duplicate | Drop exact duplicate rows. | Avoid counting repeated copies of the same transaction line. |
| Revenue | Compute `TotalPrice = Quantity * UnitPrice`. | Convert each line into its extended sales value. |

In the recorded run, the sequential removals were 135,080 missing-customer rows, 8,905 cancellation rows, 44 price rows, 34,793 non-numeric stock code rows, and 4,810 duplicates. The resulting 358,277 rows are used for RFM aggregation. Since filters run sequentially, the counts are stage-specific and must not be summed as if the categories were independent.

**Developer check:** the current cleaner does not explicitly reject negative `Quantity`. Review returns/credit notes in the source data before treating `Monetary` as net or gross realized revenue. The total above is line value, not necessarily recognized accounting revenue.

## 4. Explore Before Modeling

`eda.py` makes five charts and prints short interpretations. They inspect:

- customer monetary-value distribution and one-invoice customers
- transaction counts by country
- monthly sales totals over time
- pairwise RFM correlations
- highest-sales product descriptions

Use these plots to form questions, not to claim causation. Country bars count transaction lines, not unique customers. Monthly peaks and troughs alone do not prove recurring seasonality; recurring calendar patterns require comparing the same seasons across multiple years. The source covers approximately one year, so seasonal conclusions should be cautious.

Charts are saved to `outputs/figures/`; their axis units and legends define what each value means. The EDA functions also print interpretation text in the run console.

## 5. Engineer Customer-Level RFM

`build_rfm` in [features.py](features.py) groups cleaned transaction lines by `CustomerID` and creates one row per customer. The snapshot is the latest invoice timestamp plus one day by default.

For customer $i$:

$$
R_i = \left\lfloor \text{snapshot} - \max(\text{InvoiceDate}_i) \right\rfloor_{\text{days}}
$$

$$
F_i = \left|\{\text{unique InvoiceNo}_i\}\right|, \qquad
M_i = \sum_{j \in i}\text{TotalPrice}_j
$$

- **Recency:** elapsed days since the customer's latest purchase; smaller is more recent.
- **Frequency:** count of distinct invoices, not count of transaction lines.
- **Monetary:** sum of line-item `TotalPrice` for the customer.

The recorded snapshot is `2011-12-10 12:50:00`, with 4,314 customers in the final RFM table. The code asserts non-negative recency, at least one invoice per customer, non-null monetary values, and unique customer index.

## 6. Transform and Scale the Features

RFM metrics have different scales and skew. `scale_rfm` applies `np.log1p` by default and then fits `StandardScaler`:

$$
x' = \log(1 + x), \qquad z = \frac{x' - \mu_{x'}}{\sigma_{x'}}
$$

The function returns both the transformed DataFrame and fitted scaler. The DataFrame keeps the original customer index and the three RFM column names. Scaling is important for distance-based methods because monetary values could otherwise dominate recency and frequency.

**Important assumption:** `log1p` requires values greater than -1. Check customer monetary totals before this transform, especially if returns or negative quantities are present. For deployment, fit the scaler on training/reference data and reuse that fitted scaler when scoring new customers; do not refit it independently on every scoring batch.

## 7. Select and Compare Clustering Methods

`clustering.py` implements three complementary approaches.

### KMeans

`find_optimal_k` evaluates `k = 2` through `10` (skipping invalid values for small samples), recording:

- **Inertia:** sum of squared distance from each sample to its assigned centroid. It falls as clusters are added, so look for diminishing returns rather than a minimum.
- **Silhouette score:** compares within-cluster cohesion with separation from other clusters; closer to 1 indicates better separation, values near 0 indicate overlap, and negative values can indicate poor assignments.

The main pipeline chooses the candidate with the highest silhouette score. KMeans uses `random_state=42` and `n_init=10` in the candidate search. This is an explicit selection rule; it does not guarantee the business-optimal number of segments.

### Agglomerative hierarchical clustering

`fit_hierarchical` uses Ward linkage and the chosen cluster count. It builds a hierarchy by merging observations/clusters. Memory use is approximately $O(n^2)$, so it can become impractical as customer count grows.

### DBSCAN

`fit_dbscan` uses `eps=0.5` and `min_samples=5`. DBSCAN discovers dense groups rather than accepting a requested cluster count. Label `-1` denotes noise. The comparison excludes noise when scoring silhouette; if fewer than two non-noise clusters remain, the reported silhouette is NaN. One giant group plus noise is a valid algorithm result and should be reported rather than hidden.

`compare_algorithms` reports each method's cluster count and silhouette. Compare cluster separation alongside stability, size balance, interpretability, and campaign usefulness; no single metric selects the best business segmentation.

For the recorded run, maximum-silhouette selection chose **2 KMeans clusters**, with sizes **1,665** and **2,649**, and a silhouette score of **0.4312**. That score indicates some structure with noticeable overlap; it is not proof that two groups are the only meaningful business view.

## 8. Profile and Name the Segments

`profile_segments` joins each RFM row to its cluster label, then calculates:

- customer count (`Size`)
- mean Recency, Frequency, and Monetary value
- share of total monetary value (`RevenuePct`)
- a heuristic business name derived from each cluster's RFM means relative to the overall population

The naming rules compare relative standard-deviation scores. They can assign labels such as Champions, New Customers, At Risk, Hibernating, or Loyal. These are convenient summaries, not learned ground truth. With only two clusters in the recorded run, not every named archetype can appear. Always interpret the measured profile table before using a name in business communication.

`visualization.py` creates the candidate-k plot, cluster scatter, standardized segment profile plot, and classifier confusion-matrix chart. The scatter shows only the first two scaled dimensions, Recency and Frequency; Monetary is omitted from that two-dimensional view. The profile chart z-scores cluster means across clusters to compare relative shape, so read the numeric profile table for actual days, invoices, currency, and revenue shares.

## 9. Train and Evaluate the Segment Classifier

`train_segment_classifier` in [classifier.py](classifier.py) makes an 80/20 train/test split using `stratify=y`, then trains a 200-tree `RandomForestClassifier` with seed 42. Stratification preserves the approximate label proportions in both splits.

`evaluation.py` reports accuracy, per-class precision/recall/F1, and a confusion matrix. `get_feature_importance` sorts the fitted Random Forest's impurity-based `feature_importances_` values. The run signature records classifier accuracy **0.9942** and `Frequency` as the top feature.

Interpret metrics together. Accuracy is the share of held-out rows classified correctly; the confusion matrix shows which cluster labels are confused; per-class recall shows the fraction of each cluster recovered. Weighted metrics account for class sizes but can hide poor performance on a small class. The high score here is expected when the clusters are sufficiently separable by the same RFM coordinates used to create them.

Feature importance indicates which input dimensions the Random Forest used most to reconstruct KMeans assignments. It is not causal importance and is not a measure of the feature's value for future customer retention.

## 11. Interpretation and Methodological Limits

The current pipeline is useful as an exploratory, retrospective segmentation exercise, but it does **not** yet meet a rigorous future-purchase prediction objective:

1. KMeans is fitted to all scaled customers and creates labels before the classifier split.
2. The Random Forest is trained and tested on those generated labels using the same RFM features that formed the clusters.
3. The test labels are therefore not independent future outcomes; the high accuracy measures how well a supervised model approximates the clustering boundary.
4. No future observation window or customer outcome is defined.

To study future behavior, select a cutoff date, compute predictors using only transactions before the cutoff, define an outcome after the cutoff (for example, purchase/no purchase during the next 90 days or future spend), and hold out a later period. Ensure customers and dates are split to match the intended production use. Evaluate a simple baseline, class-specific metrics, calibration where relevant, and business utility in addition to accuracy.

For segmentation, assess repeatability under resampling or time windows, document the business interpretation of profiles, and test campaign outcomes with a control group. Do not claim marketing impact until an experiment measures it.

## 12. Developer Practice Questions

1. How would a 30-day change to the RFM snapshot change Recency, and should that affect customer membership?
2. Which transaction rows could represent returns or adjustments, and should Monetary be gross or net of them?
3. Does the top silhouette candidate also produce segments large and distinct enough for a campaign?
4. How stable are the segments if you vary `random_state`, the date window, or the scaling transform?
5. What future-purchase outcome and prediction horizon would make the classifier useful to a retention team?
6. How would you design a time-based holdout and a controlled campaign to establish business value?
